## 0. Spec baseline: which M3 do we target?

M3 has had three visible revisions, and our preset mixes them:

| Revision              | What changed for components we have                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| M3 baseline (2021–22) | The anatomy most of the preset follows.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| M3 update (late 2023) | **Slider:** the round handle and its circular state layer become a narrow bar handle with gaps on both sides, plus stop indicators. **Progress:** gap between indicator and track, stop indicator at the end of a determinate linear track.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| M3 Expressive (2025)  | **Button:** five sizes (XS–XL), round/square shapes, toggle, shape morphs on press/select. **Icon button:** five sizes, three widths, toggle. **FAB:** small deprecated, medium (80 dp) added, surface colour deprecated. **Extended FAB:** small/medium/large replace the original. **Slider:** sizes XS–XL, vertical, centered, inset icon. **Progress:** wavy shape, thick track. **Nav bar:** shorter, horizontal items. **Nav rail:** collapsed/expanded, expanded replaces the drawer. **App bar:** medium/large flexible replace medium/large, search app bar added. **List:** standard/segmented. **Search view:** contained style. New: button group, split button, FAB menu, loading indicator, docked and floating toolbars. Deprecated: segmented button, navigation drawer, bottom app bar, small FAB, medium/large app bars. |

**Decision (2026-10-20): target M3 Expressive, and keep what it deprecates.** Deprecated
sizes, colours and styles stay available as variants; only Expressive's values are the
defaults. Size names follow Expressive's. Anything removed must say why.

### 1.9 Angular Material parity (decision 2026-10-20)

Angular Material is the practical reference for components M3 doesn't specify. We build
these too, since apps need them. They follow the same rules as every other component
([guidelines](component-guidelines.md)): M3 tokens and roles for colour, shape and type, the
theme's density, direction, motion and indication, and zag for behaviour where it has a
machine. M3 gives no anatomy for them, so the parts come from Angular's own M3 token sets and
zag's part lists, and a design call is recorded in the component's output context.

| Component                   | Our name      | Behaviour                   | Notes                                                                                                     |
| --------------------------- | ------------- | --------------------------- | --------------------------------------------------------------------------------------------------------- |
| Expansion panel / accordion | `accordion`   | zag `accordion`             | Also the base for expandable list items (§2.3).                                                           |
| Stepper                     | `stepper`     | zag `steps`                 | Horizontal and vertical; step header, connector, content.                                                 |
| Paginator                   | `paginator`   | zag `pagination`            | Range label, page-size select (reuses `select`), previous/next icon buttons.                              |
| Tree                        | `tree`        | zag `tree-view`             | Nodes use `listItem` parts; expand icon in `trailing`, nested group indented.                             |
| Table, sort header          | `table`       | own (sort state, selection) | Header, row, cell, footer, sort arrow, optional selection column. No zag machine.                         |
| Grid list                   | `gridList`    | none                        | Layout only: columns, gutter, tile aspect.                                                                |
| Button toggle (group)       | `buttonGroup` | zag `toggle-group`          | Already planned (§4.0); Angular's `mat-button-toggle-group` is the connected, selectable form.            |
| Sidenav (drawer container)  | —             | —                           | Not a separate component: a side sheet or expanded rail (`modal`, `coplanar`) plus the page's own layout. |

These come after the M3 components in the order (§6), since several reuse them (`listItem`,
`select`, `iconButton`, the side sheet).

## 2. Part and variant relevance for the components we have

For every suggestion (from zag, Material Web, Angular or the M3 anatomy), three checks:

1. **Is it in the current M3 anatomy?** From the Android docs' Anatomy sections.
2. **Is it already covered?** By a state or variant in `packages/preset/src/components`,
   or by an element the Solid binding already renders. The select, menu, tooltip and dialog
   bindings already render zag's trigger, positioner and content, and the dialog renders
   zag's backdrop with the scrim's styles.
3. **Does it need its own styles?** A preset part is a style target. Parts that only carry
   behaviour or ARIA (positioner, hidden input, tab panel) don't need one.

**Verdicts:** **Add** = add now · **Variant** = add as a variant, not a part ·
**Later** = add with the feature that needs it · **Skip** = covered, or no benefit ·
**Remove** = obsolete under the current spec ·
**Split** = becomes its own component (§4.0)

## 4. Components to split

### 4.0 When to split vs use a variant

Make it a **separate component** when any of these hold:

1. **Different parts.** It adds or drops a _group_ of parts, so a combined anatomy would be
   full of "only in variant X" parts. One optional part (an extended FAB's label, a
   badge's label) doesn't count; that's what optional parts are for.
2. **Different behaviour or machine.** Another zag machine, a different interaction model
   (hover vs focusable popup), or a second interactive target.
3. **Different layout model.** The structure changes, not just colour, size, shape,
   elevation, spacing or orientation.

Keep it a **variant** when the parts are the same and only tokens, layout options or a
behaviour flag (`modal`) change. Variants already built aren't listed below. A new variant follows §5.2, so it doesn't multiply compounds. Split components can still share tokens, machines and
structure through the preset's shared helpers, as `navigation.ts` does for the bar and rail.

### 4.1 Snackbar vs toast

|                       | M3 snackbar                                                               | Toast (zag / Sonner style)                                                               |
| --------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| How many show at once | One. Others wait in a queue and appear in turn                            | Several, stacked or overlapping, up to a `max`                                           |
| Position              | Bottom edge (centre, or start on large screens), above the FAB or nav bar | Any corner or edge (`placement`)                                                         |
| Content               | Supporting text (1–2 lines), one optional action, an optional close icon  | Title + description, action, close                                                       |
| Types                 | None (always the inverse-surface colours)                                 | success, error, warning, info, loading; `promise()`                                      |
| Interaction           | Times out (4–10 s), or stays open while it has an action; no swiping      | Pauses on hover or when the window loses focus, swipe to dismiss, stack expands on hover |
| Spec status           | In the M3 spec; Angular `MatSnackBar` follows it                          | Not in the M3 spec                                                                       |

- **`snackbar`**: stays M3. Keep the anatomy and our own machine; add a queue that shows one
  at a time, and placement relative to the FAB and nav bar. zag's toast store limited to one
  was considered, but it's unconfirmed that it queues instead of dropping, and it brings
  stacking and swiping we'd turn off.
- **`toast`**: new, outside M3, skinned with M3 tokens. zag `toast`. Anatomy: `group, root,
icon, title, description, actionTrigger, closeTrigger`, plus a `type` variant. Error maps
  to M3 error colours; success and warning need custom colour roles.
- Both can share one "notify" API and the same colour tokens.

### 4.2 Plain tooltip vs rich tooltip

- **`tooltip`** (plain): `root, caret` (optional), `supportingText`, on zag `tooltip`. Opens on hover or focus;
  no interactive content. Built in c2a; the `variant` group (`plain`, `rich`) is removed.
- **`richTooltip`**: `root, caret, subhead, supportingText, actions`. Built (c2a) on zag `tooltip`
  with `interactive` on, so the pointer can move onto it. Zag's `popover` and `hover-card` aren't
  installed (adding them needs a catalog entry), and the hover behaviour is what the tooltip needs;
  see the c2a context. Trigger and positioner are rendered by the binding.

## 5. Cross-cutting issues

1. **Two anatomies drifting apart.** The `*.anatomy.ts` files in `packages/machines` are
   smaller than the preset's: slider (2 vs 6 parts), text-field (4 vs 7), navigation (4 vs 6),
   button (3 vs 4). **Done (c0b):** `packages/machines/src/anatomy-drift.spec.ts` tests every
   machine anatomy against `@pureform/anatomy`; button, navigation and text field are fixed, the
   slider joined the test when c1g moved it to zag `slider`.
2. **Variant explosion.** Every new variant group must avoid compounds where it can
   (`component-architecture.md` §5.5):
    - A variant sets one of the component's tokens, and another variant (or the base) reads it:
      the `color` group's `accent`, the size's `squareRadius` and `pressedRadius`.
    - When a value depends on two groups, one sets a literal and the other a 0/1 **flag**, and
      `blend(from, to, flag)` picks between them: `corner` sets `square`, `width` sets `narrow`
      and `wide`, `inset` sets `insetStart` and `insetEnd`.
    - **Never chain variant-set tokens** (a variant setting `a: ref("b")` where another variant
      sets `b`). CSS resolves it, but React Native resolves `b` from the theme default, not the
      variant, so the two targets disagree. Tokens the theme or instance sets (per-size tokens such
      as `heightSmall`) are fine to read directly in a variant's styles.
    - What stays compound needs a token value from one group _and_ a colour role from another
      (each fill's toggle colours, 5 each on button and icon button), or a size that a `shape`
      would otherwise tie with (the FAB's corner radius, 4).
    - Compounds across the preset: 17 before the Expressive work, 21 after (the button's 5
      toggle compounds are new; the FAB went from 5 to 4).
    - The selection space still grows with each group: the icon button now has about 1.4
      million combinations. Tests that enumerate every combination sample past 40,000: `rn-adapter`'s codegen test
      (an even spread plus each value), and the browser suite's Panda factory test (every
      pair of values from every two groups, so each compound is covered, plus an even spread).
3. **Theming concepts every new variant must keep.** Checked for the Expressive work:
    - **Density:** sized heights and widths add `densityOffset` (button, icon button, including
      the blended widths). Components without density before (FAB, slider, switch, nav) still
      have none.
    - **Shape:** every radius comes from the theme's roles (`radius("small")`, …), scaled or
      combined where Material's value has no role: 2px is `extraSmall × 0.5`, 3px
      `extraSmall × 0.75`, Expressive's 20px `large + extraSmall`. A shape theme (`sharp`,
      `soft`, `squircle`) then rescales them; `corners.ts` adds the theme's corner style
      wherever a radius is set. `packages/preset/src/radii.spec.ts` fails on any fixed px radius
      in a style or a token. This fixed the bar slider and the FAB's medium corner, plus the
      older checkbox box and tab indicator. Components whose geometry is the shape (circular
      progress, the loading indicator) are the exception: see the guidelines' shape rule.
    - **Colour groups:** colours come from group tokens or the `color` variant, never a fixed
      role where a group should apply. The nav label's `secondary` follows the group's main
      colour.
    - **Direction:** logical properties only (inline insets, `borderStartStartRadius`, block
      margins for the vertical divider), so right to left needs nothing extra.
    - **Interaction source:** pressed styles read the `pressed` state (`:active` or
      `data-pf-active`), so a press forwarded by a shared source morphs corners and narrows the
      slider's handle. `selected` also matches `aria-current`/`aria-selected`, so the corner
      swap is gated by the `toggle` variant's `toggles` flag.
    - **Indication:** the bar slider has no state layer, so its declared surface (`stateLayer`)
      stays hidden. Only the focus ring and the handle's press show. The round slider keeps the
      surface, so the indication suites (component suites, React Native) test the round slider;
      the slider suite also renders `round` and `large` examples. Compose 1.5 adds an
      **inset focus ring**, drawn inside the component rather than outside it or as an opacity
      layer (§0.1). **Done (c0d):** `materialState(..., { focusRing: "inset" })` sets the ring's
      offset to minus its thickness for every component at once; `outer` stays the default.
    - **Motion:** moving tweens (corners, the handle's width and position) go through
      `motionTransition`, so reduced motion drops them and keeps colour fades.
    - **Theme and instance tokens:** per-size tokens can be retuned by a theme or an instance.
      Flag tokens (`square`, `toggles`, `narrow`, `wide`, `insetStart`, `insetEnd`) are
      component tokens too, so an instance can set them, but the variants are the intended
      interface.
4. **Containers.** Only `list`, `chipSet` (with its behaviour) and `buttonGroup` (new) need
   styled containers. Radio group and tab list are rendered by the bindings and need no styles.
5. **Badges are composed, not parts.** Nav bar, rail and tabs place the badge component
   against an existing part. Check that `icon`/`indicator`/`tabContent` are positioning
   contexts.
6. **Deprecated components.** Don't build segmented button, navigation drawer, bottom app
   bar or the non-flexible medium/large app bars; their replacements cover them.
7. **Repo issues found while testing** (not caused by this work). All fixed, and
   `omni run build test -f all` passes:
    - The snackbar focus-timer test and the right-to-left tooltip tests failed when an earlier
      test left the pointer over them; both now park it first.
    - Rebuilding `packages/cli` dropped the executable bit from `dist/pureform.mjs`; the build
      now restores it.
    - Screenshots used the machine's fallback font, and Chromium's `color-mix` varies in the
      sixth decimal. The browser suite now bundles Roboto and JetBrains Mono and rounds
      indication colours to four decimals.
    - Still open: omni's cache can replay an older build or `generate` output after files
      change back (for example after a stash). Force with `-f all`, or regenerate the fixture
      directly.
