  `surface(container, content, elevation)` and the `stateTransition`. The rest differs. The app
  bar's root is a wrapping row at full width with a fixed edge height and `level0`. The toolbar
  is an `inline-flex` pill or a docked bar, with `orientation` choosing the axis, padding and

## Investigations

### (a) Panda: a later variant doesn't override an earlier one

**General, and some of it is visible.** Panda emits a slot recipe's variant classes sorted by
class name (`appBar__content--centered_true`, `--collapsed_true`, `--search_true`,
`--size_largeFlexible`, `--size_mediumFlexible`; seen in `panda cssgen` for the fixture), not in
the order the groups are defined. The CSS and Tailwind targets emit them in definition order.
Both are one class each in the `recipes` layer, so the later rule wins. When two variant groups
set the same property on the same slot, the targets disagree whenever the alphabetical order of
`group_value` goes against the definition order.

A script over `pureform()`'s recipes found the pairs where Panda picks the earlier group: 61
pairs across 6 components (approximate: condition-nested values compared by path):

- **circularProgress** (12): `indeterminate: true` sets the root's `borderBlockStartColor`/
  `borderInlineEndColor` to `activeColor`, and `color: secondary…info` sets them to the role.
  On CSS the colour wins. On Panda, `indeterminate_` sorts after `color_`, so **an
  indeterminate circular progress with a non-primary colour draws in `activeColor` (primary) on
  Panda**. Confirmed in the generated CSS: `.circularProgress__root--color_secondary` at line
  8422 comes before `--indeterminate_true` at 8438, while the CSS demo's order is the reverse.
- **iconButton** (35): `variant: outlined` sets the outline's `borderWidth` to `outlineWidth`,
  and every `shape` sets it to 1px, or 0 under `clipShape` (the clip draws the outline). On
  Panda, `variant_` sorts after `shape_`, so a shaped outlined icon button keeps its border where
  the clip should replace it.
- **card** (7): `interactive: false` sets the root's background and colour with the action
  area's state layer. `variant` sets them flat. On Panda the variant wins, so a card with an
  action area loses its root state layer.
- **appBar** (4): `search: true` sets the content's inline padding, and the flexible sizes set
  it too. On Panda the size wins. This is c4b's finding. Its other example, `collapsed`, sets no
  conflicting property, because c4b worked around it by selecting `size: "small"` in the
  bindings.
- **sideSheet** (2): `coplanar: true` sets `zIndex: base`, and `modal` sets `dialog`/`raised`.
  On Panda the modal's z-index wins.
- **toolbar** (1): `placement: docked`'s `width: 100%` against `orientation: vertical`'s width.
  On Panda the docked width wins, a combination that isn't really meant to be used.

**Proposal (changes output):**

1. Add a preset spec that fails when two variant groups set the same property on the same slot,
   unless they're listed with a reason. It is the script above as a test.
2. Fix each case the §5.5 way, so the groups don't overlap:
    - circularProgress: `color` sets an `activeColor`-style token, and `indeterminate` reads it.
    - iconButton: `shape` sets a `shapeOutlineWidth` 0/1 flag, which the outline reads through
      `blend`.
    - card: `interactive: false` sets a token.
    - appBar: the content padding becomes a token that `search` sets.
    - sideSheet: a `zIndex` token set by `modal` and `coplanar`, or one group with three values.

    Each changes `JSON.stringify(pureform())` and the CSS, but not what the CSS target draws.

The alternative is for the Panda adapter to move overlapping variants into `compoundVariants`.
That hides the problem instead of fixing it, and React Native's order would still need checking.

### (b) Token-driven wavy progress instead of c4a's 4 compounds

**Mostly possible: 25 → 22 compounds, with an output change.** A shape point is a
`NumericValue`, which already allows `calc` and refs, so the wave's points can read tokens
instead of baking in the default thickness:

- **Linear:** `waveBand` writes its `y` in percent of a box drawn for 4px or 8px. Written in px
  from the tokens instead, each point becomes
  `calc(amplitude + height / 2 ± height / 2 − s × amplitude)`. Then the band follows `height`,
  which `thickness: thick` already sets, and the `{ wavy, thick }` compound goes. Retuning
  `amplitude` would also move the clip, which c4a lists as a gap.
- **Circular:** a `wavyRing` point is `50% + cos θ × (R ± T/2 + s × A)`, with
  `R = 50% − A − T/2`. That's linear in `thickness` and `amplitude`, so one ring reading the
  tokens replaces the `{ wavy, thick }` and `{ wavy, indeterminate, thick }` compounds.
- **What stays compound:** `{ wavy, indeterminate }` on the circular progress. The ring clips
  the root spinner only while indeterminate. A determinate root can't take the clip, because
  the wave's troughs would cut the flat track. That needs one group's token (the clip) and
  another group's condition, the §5.5 exception.
- **Costs and risks:** CSS `shape()` gets a `calc()` per point (36 to 72 points per ring), so
  the CSS grows. React Native must resolve refs inside shape points per token set: rn-adapter's
  `shapeCoordinates` takes resolved values, so this needs checking with a spec before relying
  on it. The circular wavy is flat on React Native anyway.

### (c) Containers recolouring their icon buttons (Compose's `LocalContentColor`)

Today the vibrant toolbar's `content` token sets only its root's `color`. The icon buttons'
standard fill reads its own tokens (`primary`), so on `primaryContainer` they stay `primary`.

- **Web alone could cascade.** Custom properties inherit, so a toolbar root that set
  `--pf-components-iconButton-…` would recolour every nested icon button on CSS, Tailwind and
  Panda. But a recipe may only set its own component's tokens. React Native has no inheritance,
  so it would draw the old colours: the chained-token disagreement §5.5 forbids, just moved
  across components.
- **`currentColor` in the icon button's standard fill:** it works on the web (it inherits the
  toolbar's `color`), but it would also follow any parent's `color`, outside a toolbar too. It
  also changes standard icon buttons everywhere, and React Native has no `currentColor` for a
  view's children.
- **Proposed: descendant tokens, declared in the preset and carried by the bindings.** A
  container's recipe declares tokens it gives nested components, as data. For example, the
  toolbar's `vibrant` gives `iconButton.standardContent: ref("content")`.
    - On the web, the generator emits them as custom properties on the container's root, where
      they inherit.
    - In React Native (and in Solid/React when unstyled or inline), a binding-core
      `ContentTokens` context reads the same declaration. The container provides it, and the
      icon button merges it as instance tokens (`withSetTokens`).

    The value is resolved at the container, so there's no chained-token problem. The app bar's
    trailing icon buttons (`trailingColor`) and a navigation bar would use the same mechanism. It
    changes the output (new tokens, new rules), and it needs a design note in
    `component-architecture.md` (§5.5 or §9) first.

- **Smaller stopgap:** a toolbar-only `iconButton` colour (`color: onContainer`) that the
  toolbar's ready-made picks when `vibrant`, as Android's `FloatingToolbar.IconButton.Vibrant`
  does. Composed parts would have to pass it by hand.

## Deviations from the design

None. Public additions only: `morphSequence` in `@pureform/core/ast` (the preset still exports it
from `shape-paths.ts`). Internal additions: `plainParts`/`PlainPartProps` in the Solid and React
`parts.tsx`, and `MENU_TRIGGER_ATTRIBUTES` in Solid's `menu/menu.tsx`. Nothing was renamed or
removed. `morph()` keeps its signature, result and error.

## Refactoring hints (for c5)

- **Reuse:**
    - `plainParts(context.use, "div" | "span")` for any part that is just an element with the
      user's props (a picker's header, its grid's sections).
    - Core's `morph`/`morphSequence` for any shape that animates.
    - `surface()`, `iconBox`, `stateTransition` and `pressableRoot` from `shared.ts`.
    - `dialogParts` and `useModalOverlay` (r3) for the modal date and time pickers.
    - `selectFieldParts` (r3) for a docked date picker's field, if it is select-like.
    - `useMachineButton` for the pickers' plain buttons.
- **Avoid:** two variant groups setting the same property on one slot. Panda orders them
  alphabetically (investigation a). Set a token in one and read it in the other.
- **Roving keys:** the pickers' day grid moves by arrow keys in two dimensions, which is neither
  `toolbarKeyTarget` (wraps, one axis) nor the carousel's `keyTarget` (clamps). Use Zag's date
  picker keys rather than a third copy.
