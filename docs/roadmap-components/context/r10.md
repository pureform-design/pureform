## Decided work

### React Native toast swipe (done)

- **How:** `ToastItem` (`react-native/src/toast/toast.tsx`) wraps its pressable in an
  `Animated.View` moved by `useToastSwipe`: a sideways pan (`useSidewaysPan`, below) moves it and
  fades it (gone at its own width); let go, `toastSwipeRelease` decides: past half its width or a
  flick its way (0.5 px/ms) it slides out (200 ms, `cubic-bezier(0.2, 0, 0, 1)`, as the web) and
  dismisses, else it settles back. Reduced motion jumps. `useHeldTimeout` takes an `alsoHeld` flag,
  so the timer waits while the swipe holds the toast. A `closable: false` toast doesn't move.
  Sideways at every placement (decided).
- **Shared:** `toastSwipeRelease` and `TOAST_SWIPE_VELOCITY_THRESHOLD` moved to
  `binding-core/src/components/toast.ts` (root export), used by the web's `toastSwipeToDismiss`
  and React Native; `TOAST_SWIPE_VELOCITY_THRESHOLD` is still re-exported from `/dom`.
- **Tests:** React Native `overlays.spec.tsx` "swipes a toast away sideways past half its width,
  holding its timer meanwhile" and "settles a short swipe back, and doesn't move a toast that can't
  be closed" (animated and reanimated); binding-core `toast-swipe.spec.ts` `toastSwipeRelease`.

### Shared drag skeleton (refactor rule passed)

- **Web, `binding-core/src/sideways-drag.ts`** (`sidewaysDrag`, `/dom`): the pointer skeleton the
  side sheet's drag and the toast's swipe repeated (accept on down, slop, axis lock, capture,
  velocity, release/cancel, swallowing the click after a drag). Hooks: `accepts`, `down`, `start`,
  `move(dx)`, `release(dx, velocity, cancelled)`. `side-sheet-drag.ts` and `toast-swipe.ts` keep
  only what differs (the coplanar holder, `closeAsker`, `settleTransition`; the toast's WAAPI fade
  and timer). Checks: same concept (a sideways drag that dismisses), obvious (the same 60 lines
  twice), flexible (hooks for each phase; a dismissible chip would fit).
  Small behaviour unifications, both within the old tolerances: the toast's slop is now measured
  as the sheet's (larger axis ≥ 8 px, was the hypotenuse), and the toast's velocity includes the
  `pointerup` sample, as the sheet's did; the sheet's moves now `preventDefault`, as the toast's
  did. Tests: `sideways-drag.spec.ts` (new, 3), `toast-swipe.spec.ts`, `side-sheet-drag.spec.ts`,
  `side-sheet.e2e.test.ts` in the gate.
- **React Native, `react-native/src/sideways-pan.ts`** (`useSidewaysPan`): the `PanResponder` the
  side sheet and the list item swipe repeated (capture on the way down past the slop, mostly
  sideways; grant, move, release with `vx`, terminate), handlers read from the latest render. Used
  by the side sheet, the list item and the new toast swipe. Tests: React Native side sheet and list
  item specs, the toast specs above.
- **Declined:** the web list item's swipe (`react/src/list-item/swipe.ts`, Solid's alike) is

### FabMenu focus follows the highlight (done)

- **How:** `fabMenuListProps` (binding-core) runs Zag's keydown, then on ArrowUp/Down, Home or End
  focuses the item Zag highlighted (`[role^=menuitem][data-highlighted]`, a frame later, once the
  binding has drawn it). With the items already tabbable and highlighting on focus, arrows and Tab
  now move one focus. Zag's `focusMenu` doesn't take focus back: it only focuses the content when
  focus is outside it.
- **Tests:** `overlays.e2e.test.ts` "moves focus with the highlight on the arrow keys, and Tab goes
  on from there" (solid/css, react/panda: passed; whole suite in the gate).

### Menu `submenu="auto"` by measured room (done)

- **How:** binding-core `menuSubmenuRoomOf(menu, boundary)` (the wider side beside the menu, and
  the menu's own width as what a submenu needs) and `menuSubmenuMode(submenu, room)`: `auto`
  cascades when `beside >= needed`, drills otherwise, cascades before it's measured (server
  render). `/dom`: `menuSubmenuRoom(content, anchor)` bounds by the window and every ancestor of
  the trigger that clips sideways (`overflow-x` not `visible`: a narrow side panel), and
  `watchMenuSubmenuRoom` measures two frames after opening and on window resize. React and Solid
  render a `MeasureSubmenuRoom` inside the ready-made's content while `auto` (as
  `HighlightOnDrill`); React Native measures the menu surface (`measureInWindow` on layout) against
  the window.
- **Deprecated option removed:** `MENU_CASCADE_MIN_WIDTH` and the window-width
  `menuSubmenuMode(submenu, width)` (replacement: `menuSubmenuRoomOf` + the new
  `menuSubmenuMode`). READMEs (react, solid, react-native) updated.
- **Tests:** binding-core `menu.spec.ts` (`menuSubmenuMode`, `menuSubmenuRoomOf`); React and Solid
  `menu.spec.tsx` "cascades by default when a submenu fits beside the open menu, and drills when its
  container is narrow" (the test registry's menu is 60 px wide, so the panel is 70 px); React Native
  `components.spec.tsx` "cascades by default when a submenu fits beside the menu, and drills when
  it doesn't" (a centred menu in a 1000 vs 320 wide window).

### React Native Web cascaded submenu on the keyboard (done)

- **How:** `Popup`'s key handling is now `MenuKeys` (arrow keys, Home, End; `onKey` hears other
  keys first); the cascaded submenu (another portal entry) gets its own. On the web an item with a
  submenu opens it on the arrow toward the inline end (ArrowLeft under RTL), and the submenu
  focuses its first item; the arrow toward the start, or Tab, closes it and focuses its item
  again. Pressing still toggles it. Nested cascades work the same way (each level is a `MenuImpl`).
- **Tests:** React Native `overlays.spec.tsx` "opens a cascaded submenu with the arrow toward the
  end and backs out with the other, on the web" (both engines).

### React Native DateInput follows a controlled `value` (done)

- **How:** `date-input.tsx` remembers the last value it saw; when `value` changes to one the
  segments don't already make (`dateFromSegments`), it rewrites the digits (`dateSegmentTexts`).
  Values the segments made themselves (including a partial date's empty one) leave the digits and
  focus alone.
- **Tests:** `date-pickers.spec.tsx` "follows a controlled value changed later, keeping focus and
  the digits it typed" (fails without the fix).

## Refactoring hints

- **Reuse:** `sidewaysDrag` (web) and `useSidewaysPan` (React Native) for any sideways drag or swipe
  (a dismissible chip, a snackbar swipe); `toastSwipeRelease` for a swipe-to-dismiss decision;
  `menuDrillPick`/`menuDrillLevel` for drilled menus; `menuSubmenuRoomOf` and
  `watchMenuSubmenuRoom` for anything that chooses a layout by the room beside an open popup;
  `MenuKeys` (React Native menu) if another React Native list of items needs web arrow keys.
- **What must not change:** `sideways-drag.spec.ts`, `toast-swipe.spec.ts`,
  `side-sheet-drag.spec.ts`, `side-sheet.e2e.test.ts`, the menu specs in all three bindings, the
  React Native toast and date input specs.

## Open questions

- `auto`'s room is the menu's own width beside it; a submenu wider than its parent menu (long
  labels) could still flip and overlap. Measuring the submenu itself would need it rendered first.
- `auto` measures once per open (and on window resize); a container that resizes while the menu
  is open keeps the first answer.
- React Native's `auto` bounds by the window only (no clipping ancestors to read).
- The React Native toast swipe isn't on the native driver for its opacity interpolation on
  devices; tested on React Native Web only.
- The toast's slop is now the sheet's (larger axis, not hypotenuse): a diagonal 6×6 move is no
  longer a swipe start. Say if the old measure matters.
