      `listColor`), so a dark scheme's list isn't white; browsers that draw the list natively ignore

## Refactoring hints

- **Helpers that look generic:** `nativeSelectGroups(items)` is `selectItemGroups` (the select's),
  retyped for items with no interaction source: one generic `groupItems` in binding-core would
  serve the select, the menu's groups, the rail's sections and this. React Native's
  `menuActions`/`textOf` (a text-only subset of a slot style, for a `Text` inside a box) would serve
  any pressable that draws a label in a boxed slot.
- **Code that looks like a sibling's:** React Native's Material-menu fallback repeats the select's
  `Menu` wiring (`select/select.tsx`: groups from items, `onSelect` to `setValue`); the select
  measures and opens its own `Modal`, this one uses the menu's `trigger`. Solid's `chosen`
  signal and `selected` options will repeat for any native control the server must render with a
  value (a radio group). The `Select`-part handling (`nativeSelectProps`, the disabled fieldset
  rule) is the checkbox's and text field's by another name.
- **Suggested home:** `groupItems` in `binding-core/src/menu-groups.ts`; the text-subset helper next
  to `iconStyleOf` in `react-native/src/icon-style.tsx`.
- **What must not change:** the `nativeSelect` preset snapshot, the indication fixtures' entries,
  the `native-selects` screenshot, the NativeSelect e2e above, `select`'s own (unchanged).

## Open questions

- **Field (c10a):** "works inside Field" is built as props, not context: the select takes `id`,
  `invalid`, `required`, `disabled`, `aria-describedby` and `aria-labelledby`. At the merge, Field
  should hand those to the NativeSelect the way it does to Input (a `useFieldControl()` or the
  same cloning), and a `FieldContext` read in `Root` would replace the props. Not testable here
  because Field isn't on this branch.
- **"The same box as Input":** built from the preset's own values (40px, extra small radius, 1px
  outline, the text field's padding and tokens' names), since Input is c10a's. If c10a's Input
  differs (height, radius, border), the two should share a `plainBox` helper in
  `preset/src/components/shared.ts`; the numbers are tokens (`height`, `radius`, `paddingInline`,
  `outlineWidth`) so a retune is one place.
- **Components 74:** c10a adds its own; the count in the gap analysis (§1.8) and its list will
  conflict at the merge and need the sum.
- **Indication:** the state layer is the root's, following the select (a hover tint, a focus tint
  and the focus ring); no ripple is drawn (a `<select>` has no layer to hold one, and the preset
  declares one only for the state layer), but the anatomy names the root as the surface, so
  `ripple` is in the usage entry. Say if the entry should drop `ripple`.
- **React Native, native paths unverified:** `MenuView`'s props (`actions`, `onPressAction`,
  `state`, `displayInline`, `subactions`, `attributes.disabled`) are from its README, not run; no
  focus or hover state on a touch trigger; the trigger's accessibility role is `combobox` on the
  pressable (the platform menu opens from the wrapping `MenuView`). The `require` of the optional
  peer is untested under Metro. A device check is needed before the peer is advertised.
- **React Native web:** hover and focus are tracked from DOM events on the raw select and pass
  `hover`/`focus` states to the slots, not through the indication source, so a shared
  `interactionSource` isn't observed there.
- **`multiple`:** not supported (a list box looks and behaves differently); the select is always
  single.
- **Peer range:** `@react-native-menu/menu` is `>=1.0.0` in `peerDependencies`; no version was
  checked against a React Native release.
