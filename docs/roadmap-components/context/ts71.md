# ts71: TypeScript 7.1 beta, prop-controls on its JS API

## What changed

- Root catalog `typescript` is `7.1.0-beta` (was `^7.0.2`); lockfile updated. Type check
  (`bunx tsc --noEmit -p tsconfig.json`) is clean in every package and app. One new error, fixed
  minimally: `packages/machines/src/table/table.connect.ts` `getHeaderCellProps({ column, sortable } = {})`
  no longer got its parameter type from the context, so it is annotated `HeaderCellProps`.
  (`tests/*` packages report missing `$recipes` / `.pureform` modules only because their generated
  output isn't there; same on 7.0.2.)
- `apps/storybook-web/scripts/prop-controls.ts` and `prop-controls.spec.ts` use `typescript/sync`
  (`API`, `createProgram`, `Checker`) and `typescript/ast` instead of `@typescript/typescript6`.
  `generate-stories.ts` calls `controlsOf.close()` so the native checker process ends.
- `@typescript/typescript6` is gone from the root catalog and dependencies, from storybook-web, and
  from `bun.lock`; nothing imports it (older roadmap docs still mention it as history).

## API differences

- The checker is a separate native process: `new API({ cwd })`, `api.createProgram(files, options)`,
  `program.getProject().checker`; call `api.close()` when done. Enum options are numbers
  (`ModuleKind`, `ModuleResolutionKind`, `JsxEmit` from `typescript/sync`; `ScriptTarget` from
  `typescript/ast`), strings panic the server.
- Symbols' `declarations` are `NodeHandle`s: `.path` gives the file, `.resolve()` the node (lazily
  fetched). `declarationFile` uses `.path` (a real path, so `binding-core` still matches).
- Types are objects with methods (`getTypes()`, `getProperty()`, `getCallSignatures()`,
  `getBaseTypes()`, `getTemplateType()`); `getSymbolOfSourceFile` replaces `getSymbolAtLocation(source)`;
  JSDoc tag text is a plain string (`displayPartsToString` is gone); boolean literals have `.value`
  (no `intrinsicName`).
- `getRootSymbols` has no equivalent. A homomorphic mapped type (`Omit`/`Pick`) copies its source
  property's declarations, so those need nothing. A property with none (`Controllable`'s `[K in N]`)
  is traced with `mappedDeclaration`: walk the props type through unions/intersections, a mapped type's
  source (`T[P]`) and an interface's bases (the target's, for a generic reference) down to the mapped
  type node, and read its file and `@control` tag from there (replacing internal `links.mappedType`).

## Output comparison and gaps

Generated stories before (TS6) and after (TS7.1) were compared (`src/stories/generated`, 79 files):

- **Same controls**: every prop, control kind, `options` set, `mapping`, and `@control` tag is the
  same (compared with keys and options sorted).
- **Not byte-identical**: 63 files list their props in another order, and 18 selects list options in
  another order. TypeScript 6 gave both in type-id (creation) order; TypeScript 7 sorts a union's
  members itself (strings and numbers by value) and orders properties differently, so the old order is
  not reproducible from the API. `prop-controls.spec.ts` expects declaration order for options
  (`["small", "large"]`, `["1", "2", "auto"]`), so options are put back in the order the declared type
  node writes them (`declaredValues`, through unions, aliases, indexed accesses). The spec's
  expectations are unchanged.
- Options still in checker order (alphabetical) because the declared type is registry-derived or built
  from several aliases: `VariantProp<…>` `color`/`density`/`variant`/`corner` on ButtonGroup, ChipSet,
  List, RadioGroup, SelectionList; `submenu` (Menu); `transition` (Stepper, Tabs); `activationMode`
  (Tabs). The old order there was TS6's incidental creation order (for example `density` began with
  `compact`), not the registry's.
- Property order differs in 63 files only in argTypes order, which sets the controls panel's row order.

## Follow-up: control order (`control-order`)

The open question above is settled: the controls' order no longer comes from the checker.

- **Props** (`orderedProps` in `prop-controls.ts`): declaration order. A union's or intersection's
  members in the order written, an interface's `extends` list in order, then its own members by
  source position; `Omit`/`Pick` follow their source type; a prop with no declaration
  (`Controllable`'s mapped keys) sits at its mapped type's position; anything unplaceable comes
  last, by name.
- **Options**: a plain literal union as written (as before); a `VariantProp<C, "group">` in the
  order the generated `ComponentRegistry` writes the group (`variantOrder` reads
  `.pureform/registry.d.ts`, the config's order), so density is `inherit, comfortable, default,
  compact, dense`; anything computed (no written order to follow) in code point order.
- Specs: `prop-controls.spec.ts` (prop order, literal order, registry order, fallback); the fixture's
  `VariantProp` now resolves through a fixture `ComponentRegistry`.
- Regenerated stories differ only in `argTypes` order and the options named above. Variant
  props whose group is in the anatomy still take the anatomy's order (`argTypeFor`, unchanged), so
  Button/Menu `density` shows the anatomy's `0, inherit, -1, …`, while List/ButtonGroup (registry
  group without an anatomy entry) show the registry's.
- Note: on a fresh worktree `omni run build` failed in `unplugin-dts` (needs
  `@typescript/typescript6`, removed by ts71). I used `bun add --no-save @typescript/typescript6`
  locally, not committed; main's build needs a decision (see open questions).
