## Decisions applied

1. **One page-transition core.** binding-core `components/page-transition.ts`: `PageKey`,
   `TransitionPage` (`key`, `state` current/entering/leaving, `direction`), `startPages`,
   `changePages(pages, key, { direction, keepLeaving })`, `settlePage`, `pagesLeaving`,
   `pagesMoving`, `keepContents`, `LEAVING_PAGE_PROPS`, `pageRootProps` and
   `PageTransitionProps` (`transition: "none" | "fadeThrough" | "sharedAxis"`, `transitionScrim`).
   The fade through keeps leaving pages through quick switches (`keepLeaving`); the shared axis
   keeps at most two (`sharedAxisChange`, which adds the direction). Gone: `showPage`, `dropPage`,
   `pageStateProps`, `FadeThroughState`, `FadeThroughPage`, `sharedAxisStart/Settle/Moving`,
   `SharedAxisPage(State)` (all unreleased). Each binding has one module beside its presence:
   React `src/page-transition.tsx` (`useTransitionPages`, `TransitionPageView`,
   `useTransitionPage`), Solid `src/page-transition.tsx` (`createTransitionPages`,
   `TransitionPageView`, `useTransitionPage`), React Native `src/page-transition.ts`
   (`useTransitionPages`). Web pages wait with `whenAnimationsEnd` (Solid a frame on).
   `useSharedAxisPage` became `useTransitionPage`, exported from both entries. Entering fade
   through pages now settle too (they drop `data-state="open"` once their animations end); on
   React Native they don't (the presence would restart).
   **`transition="fadeThrough"`** is on the ready-made tabs and a row stepper in React and Solid,
   and the row stepper in React Native (RN tabs have no panels).
   **Declined:** one generic `PageTransition` component per binding parameterised by anatomy
   (the two roots differ: the shared axis's scrim and tokens, the fade through's per-value
   content function; the shared page model and page view already hold the duplication); moving
   React Native's page motion into the shared module (the fade through runs on the engine's
   presence, the shared axis on Animated with measured width).
2. **The fade through clips while a page leaves.** `pageRootProps` marks the root
   `data-transitioning`; the preset clips it then (`overflow: clip`), not at rest, so focus rings
   and shadows show. React Native clips the root (`overflow: hidden`) while a page leaves. The
   shared axis already clips its root always (`overflow: clip`); left as it is.
3. **The shared-axis scrim** stays opt-in, off by default; binding-core's props, the preset's
   header and the READMEs say Compose draws it only behind predictive back.
4. **FAB menu.** Checked against androidx-main
   `compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/FloatingActionButtonMenu.kt`:
   Compose has neither a fixed step nor a cap. `FloatingActionButtonMenuItemColumn` animates an
   `Int` from 0 to the item count on `MotionSchemeKeyTokens.SlowEffects` (stiffness 800,
   critically damped, `visibilityThreshold = 1`), showing each item as the count passes it; each
   item's width runs on `FastSpatial` and its alpha on `FastEffects`. That spreads the items over
   about 90ms (3 items: gaps ~33, ~58ms) to 150ms (8 items: gaps ~15–50ms). Adjusted: the step is
   `FAB_MENU_STAGGER = 25ms` (evenly spaced; was `short1`, 50ms), the cap stays eight (CSS needs a
   bound for its `nth-child` rules; M3 menus hold six at most). React Native uses the same 25ms.
   The list's exit holds `(min(itemCount, 8) − 1) × 25ms`, where `itemCount` is a new `fabMenu`
   token the bindings set through `fabMenuSelection(props, itemCount)`: React's `List` counts its
   children, Solid's counts its elements (a `MutationObserver`); the ready-made passes its
   `items.length` through a context from the first render so server rendering and hydration
   agree. Also fixed: an item waiting its turn showed at full size before its enter animation
   began (`fill-mode: none` with a delay); a waited step now fills `backwards` (`both` on exit),
   as m3a's delayed fades already did.
5. **React Native shared axis** reads the instance's (and the provider defaults') `slideSpring`
   (a spring role or a spring), `fadeDuration` and `fadeDelay` (ms numbers or CSS times), falling
   back to `spatialDefault` and Compose's 90/50ms.
6. **A change during a change:** not fixed (recorded). On the web the leaving keyframes start
   from their first frame, and continuing from the current value would need the running
   animation's progress read back into CSS vars per page; in React Native the page's Animated
   values could continue, but the entering and leaving interpolations map different ranges, so
   it needs a second value per page. The jump is a fifth of the width at most, only when a change
   comes while one runs.
7. **m3d:** `OverlayCloseProps` (binding-core `dialog.ts`, with `CloseQuestion`, which moved there
   from `sheet.ts`) replaces `DialogCloseProps`, `SideSheetCloseProps` and `BottomSheetCloseProps`.
   `closeTriggerProps(close, onClose, requestClose)` replaces the copies in React's and Solid's
   `dialog-parts.tsx` and bottom sheets. Docs: an app's Cancel asks `onClose` by being a
   `CloseTrigger`; React Native surfaces alone accept `onClose` and never call it.
8. **Kept as they were:** the fade through's theme durations; no screenshot sections for the
   transitions (the e2e covers the motion); FAB items scale from their own centre; the list's
   enter-hold restriction (Zag's presence hides an exit whose animation name equals the open
   state's), left for r9.

## Refactoring hints (r9, c8)

- **Page transitions:** reuse binding-core `page-transition.ts` and each binding's
  `page-transition` module for any new switched content (navigation content, a carousel's
  pages); don't copy `useTransitionPages`. `whenAnimationsEnd` is the web's "keep until the exit
  ends" outside Zag presence.
- **Mirrored constants:** React Native restates the preset's motions (`OVERLAY_MOTIONS`), the
  FAB stagger (`STAGGER = 25`, `STAGGERED = 8` in `fab-menu.tsx`) and the shared axis's defaults
  (`SHARED_AXIS_FADE`); only the motions are checked against the preset ("are the preset's"). A
  generated mirror would cover the rest.
- **Overlay step timing:** `OverlayMotionStep.wait` (numeric, a stagger) and
  `MotionTiming.delay` (a duration role) are two ways to wait; r9 could fold them into one if a
  third use appears.
- **Presence restriction (r9):** the FAB list can't hold on enter because `@pureform/machines`'
  presence hides an exit whose animation name equals the open state's. Changing that would let
  the list hold symmetrically.
- **Item count token:** `fabMenu.itemCount` is the first token a binding sets from its children;
  a list that staggers (c8) can take the same route rather than a CSS var by hand.
- **What must not change:** `fade-through.e2e.test.ts`, `shared-axis.e2e.test.ts`,
  `overlays.e2e.test.ts` FabMenu (exact hold) and the onClose specs, the `fabMenu` snapshot in
  `split-button.spec.ts.snap`, RN `presence.spec.tsx`.

## Open questions

- **25ms step:** an even spacing of Compose's spring-driven stagger; per-count delays (front-loaded
  as the spring is) would be closer, and need the count in CSS per item. Say if wanted.
- **The shared axis clips at rest** (m3b), which can cut a page's focus rings or shadows at its
  edges; it could clip only while moving, as the fade through now does.
- **A change during a change** jumps (decision 6).
- **Fade through entering pages settle** on the web (`data-state` drops after the enter); React
  Native keeps them `entering`. Harmless, but the two differ.
- **Composed FAB menus** (`FabMenu.Root` with parts) count their items after mount, so server
  rendering a composed menu renders without `itemCount` (the CSS falls back to eight steps) and
  hydration adds it.
