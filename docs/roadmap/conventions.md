# Conventions for every phase

Every phase follows these rules. A phase's context file adds its own scope; it never
relaxes these.

## Before starting

1. Read `docs/design/component-architecture.md` (the "design doc"), at least the sections
   the phase lists.
2. Read the output context of every phase it depends on (`docs/roadmap/context/`). They
   say what was actually built, which can differ from the design.
3. Check `git log --oneline -20` for work since those contexts were written.

## Use the omni MCP first

Prefer the omni MCP's tools over the shell whenever one fits; fall back to the shell only
for what they can't do (git, formatting, linting, ad-hoc scripts).

- **Builds and tests:** `task_run` (`build`, `test:unit`, `test:e2e`, `test`), not
  `vite`, `vitest`, or `tsc` directly. It runs dependencies first and caches results.
- **Workspace facts:** `workspace_info`, `project_list`, `project_config` (a project's
  tasks and dependencies), and `hash_project`/`cache_stats` to see what changed.
- **New packages:** `generator_list`, `generator_inspect`, `generator_validate_input`,
  then `generator_run` with the `ts-package` generator, rather than copying a package by
  hand. It also registers the package in `cog.toml`.
- **Commands across projects:** `exec_command` with a directory filter, rather than a
  shell loop over packages.
- **Workspace tools:** `tool_list`, `tool_inspect`, `tool_run` for anything the workspace
  defines.
- **Ignore files and links:** `ignore_sync` after adding generated folders (such as
  `.pureform/`), and `projection_status` when links look wrong.

## Working

- **Commits:** one coherent unit per commit, with a Conventional Commits message
  (`feat(solid): …`, `refactor(preset): …`, `docs(roadmap): …`), committed with
  `GIT_EDITOR=true git commit`. Stage only the files you changed. Push when the phase is
  done.
- **Never commit:** `docs/design/handoff.md`, `dist/`, `styled-system/`, `.vitest/`,
  `.env.local`, or `apps/solid-demo/solid-env.d.ts` (regenerated by builds; restore it
  with `git show HEAD:apps/solid-demo/solid-env.d.ts > apps/solid-demo/solid-env.d.ts`).
- **Before each commit:** `bunx oxfmt <paths>` from the repo root (no `..` in paths), then
  `bunx oxlint <paths>`, then the tests.
- **Builds and tests** run through the omni MCP's `task_run`. A result with `ok: false`
  can still list completed tasks; check each `exit_code` and any
  `skipped:DependeeTaskFailure`. Its project filter may run the whole workspace; read
  the results for the projects you changed.
- **Browser tests** use Vitest browser mode (Chromium). `.env.local` sets
  `CHROMIUM_PATH`; outside omni, load it with `set -a; source .env.local; set +a`.
- **The suites' Panda setup is `tests/panda-fixture`,** not `apps/solid-demo`: the config every
  target is generated from, the Panda registry and stylesheet, and the visual suite's page. Output
  contexts written before it (p3c to p9c) say the suites read the demo; read them as the
  fixture. Change the fixture to change what the suites test, and a demo for the demo; each web
  demo has its own smoke test (`test:e2e`).
- **Older contexts' "glue"** is the generated registry (`.pureform/`), and their `pureform.glue.ts`
  (exporting `glue`) is `pureform.codegen.ts` (exporting `codegen`).
- **New packages** are scaffolded with the omni `ts-package` generator (see above).
  Dependencies go through the root `package.json` catalog. Test projects live under `tests/`.
- **Package READMEs:** every package a phase creates gets a `README.md`, and every
  package a phase changes gets its `README.md` updated (created if missing). Write it for
  a person new to the package, in plain language:
    - what the package is for, in a sentence or two, and where it sits among the others
      (what it depends on, what depends on it);
    - its architecture: the main modules and how they fit together, with a small diagram
      when it helps;
    - its public API at a glance (entry points and subpaths, with a short example);
    - how to build and test it (the omni tasks);
    - anything surprising: stubs, deliberate limits, links to the design doc sections.

    Keep it current with the code; the output context records what changed, the README
    describes what is.

- **Rebuild a package's `dist`** after changing it; dependents and scripts read `dist`.
- **Refactors must not change output.** Prove it with before-and-after equivalence on
  React Native and in Chromium (tooling: `/tmp/opencode/baseline.sh`,
  `/tmp/opencode/compare.py`, if present; otherwise write the equivalent). Changes that
  alter output on purpose are checked against explicit fixtures instead, and say so in
  the commit.
- **Prose and comments:** sentence case, active voice, no em dashes, no "§x" references
  in code. Match the surrounding comment density.
- **Types:** strongly typed authoring with working autocomplete; Material's names for
  contracts.
- **Stubs are fine** when a phase says so: a stub has the final signature, a comment
  naming the phase that fills it in, and a test marked `todo` where one belongs.

## Keeping context small

Compact the session when its context is getting large, even when running as a subagent:
commit what's finished and draft the output context first, then request compaction
(`opencode api post /api/session/<session-id>/compact --data '{}'`), then reread the
phase file and the draft. See the [roadmap](README.md) for the full steps.

## Finishing: the output context (required)

When a phase or subphase is done, write `docs/roadmap/context/<phase-id>.md` before the
final commit, and commit it with the work. Later phases read it instead of the code to
find their footing, so it must stand on its own:

```md
# <phase-id>: <title> (output context)

Commits: <first>..<last>

## Built

What exists now: packages, modules, exported APIs with their signatures, file paths.

## Deviations from the design

Anything that differs from the design doc or the phase file, and why. Update the design
doc too when the deviation is a decision.

## Stubs and gaps

Each stub or known gap, the phase expected to finish it, and where it lives.

## How to verify

The commands and tests that show it works.

## Notes for the next phases

Traps, conventions established, and anything the dependent phases must know.
```

Before writing it, make sure the `README.md` of every package the phase created or
changed is current.

Then tick the phase in `docs/roadmap/README.md` and link its output context there.
